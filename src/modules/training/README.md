# Entrenamiento personal: ejercicios y borradores

Este árbol implementa `personal_exercise.create`, `routine.create`, `routine.draft.save` y `routine.publish` del contrato 1.0.1. Sus casos no registran rutas ni publican capacidades por sí mismos. Entrenamientos, series, duplicación, selección, búsqueda/listados y sync móvil quedan fuera de esta entrega parcial.

`CreatePersonalExercise.Execute` recibe claims verificados y el comando completo. El decoder rechaza campos desconocidos, duplicados, ausentes o nulos, fechas/UUID inválidos y Unicode inválido; conserva nombres, notas y fecha capturada al calcular el hash. La creación requiere revisión inicial `0`. Las dependencias `after_operation_id` todavía no están habilitadas para este caso: producen rechazo terminal sin crear datos. El repositorio sólo admite transacciones del pool data con cuenta explícita y ámbito puro.

La UoW toma el mutex compartido de la cuenta. Antes de devolver incluso un recibo existente, se comprueban sesión activa y origen propio. El origen histórico puede estar revocado; no concede autoridad y se conserva por separado del dispositivo que realiza el intercambio. Dato, revisión canónica, recibo y grupo de cambios se confirman juntos. Un fallo posterior al journal revierte todos esos efectos y la secuencia.

El ID y el nombre no se usan de forma intercambiable: crear otra identidad con el mismo nombre es válido. Un ID ocupado nunca se actualiza; la respuesta es el mismo rechazo genérico para una colisión propia o ajena. El índice de búsqueda usa texto derivado sin cambiar el nombre visible ni el hash de la petición. No existe todavía un lector HTTP de búsqueda.

Las pruebas PostgreSQL requieren exclusivamente `MANCUERNA_TEST_OWNER_DSN`, `MANCUERNA_TEST_DATA_DSN` y `MANCUERNA_TEST_AUTH_DSN` locales y las etiquetas `server,integration`. Sin esas variables se omiten explícitamente: compilar las pruebas o pasar unitarias no acredita la integración. La coordinación central conserva la evidencia del cluster efímero. Las fixtures sólo preparan cuentas y sesiones sintéticas; el ejercicio y sus metadatos de sincronización recorren los casos y repositorios reales.

Ninguna historia se marca DONE por estos bloques. No acreditan una app móvil funcional, persistencia offline, intercambios completos de entrenamiento ni un catálogo global.

## Creación de rutina: bloque 1B

`CreateRoutine` exige el mismo actor vigente, origen propio, contexto puro y revisión inicial `0`. Crea una raíz `routine` y su `routine_draft` con el mismo ID/revisión `1`, en una sola transacción. El recibo afecta ambas entidades; el journal contiene las dos proyecciones completas en una sola secuencia. No crea versiones, no publica, no selecciona una rutina y no inventa prescripciones.

El borrador puede estar vacío o incompleto, pero siempre tiene forma cerrada. `null` es válido para referencia, series prescritas y descanso; campos/arrays ausentes o nulos, donde el contrato requiere una cadena o array, son inválidos. Las identidades de edición son únicas en todo el documento; el orden de los arrays se conserva. Crear referencias nuevas exige un ejercicio propio o de catálogo existente y no retirado. Este filtro no se aplica a snapshots históricos ni se presenta como regla universal de republicación. El recibo se consulta antes de revalidar referencias, de modo que archivar después un ejercicio no invalida un reintento ya aceptado.

La entrada JSON cruda está limitada a 2 MiB; comando canónico y grupo completo a 1 MiB. `Commands.CheckChanges` comprueba bajo mutex la secuencia siguiente real, operación y proyecciones completas, y mide el texto JSONB de `changes` antes de insertar el dato. Un grupo que no cabe obtiene un rechazo `LIMIT_EXCEEDED` durable sin efectos de datos, incluso cuando el contenido del borrador sí cabe y sólo su envoltorio de journal supera el límite conservador. El repositorio de rutina conserva además su defensa de tamaño JSONB antes de los inserts. Commit repite las comprobaciones; cualquier error posterior debe revertir dato, recibo, revisiones y secuencia, no aceptar parcialmente. La dependencia `Stream` de los constructores se conserva por compatibilidad, aunque la medición autoritativa ahora pertenece a Commands. Las defensas JSONB de snapshot siguen vigentes en su lector separado.

Las pruebas de 1B comprueban concurrencia, borradores incompletos, aislamiento, referencias retiradas, reintento después de archivado, colisiones, rollback después de insertar borrador y después del journal, y diferencias entre tamaño canónico y JSONB. Su compilación local no sustituye la ejecución en PostgreSQL que registra el harness central.

## Guardado de borrador: bloque 1C

`SaveRoutineDraft` modifica exclusivamente el borrador mediante CAS: conserva raíz, título publicado y versión actual. El journal añade una proyección `routine_draft` completa y una secuencia, junto al recibo. Un borrador descartado puede abrirse otra vez conservando su identidad y avanzando su revisión. Esto no implementa el comando de descarte. Una raíz archivada rechaza la edición; una raíz eliminada conserva la propuesta como conflicto y nunca se resucita.

`base.after_operation_id` se resuelve sólo con recibos comprometidos de la misma cuenta. Se toma la revisión afectada del borrador exacto, aunque ya exista una revisión posterior; nunca se sustituye por la actual. Una dependencia ausente o ajena sigue pendiente y no produce recibo. Una dependencia terminal fallida produce un bloqueo durable; un recibo que no afectó ese borrador se rechaza. La autorreferencia es inválida. Los ciclos entre operaciones aún pendientes no pueden resolverse mediante esta tabla de recibos terminales: permanecen pendientes, sin inventar una cola persistente o dar por implementado su tratamiento móvil.

Las referencias siempre deben existir y pertenecer a la cuenta, salvo catálogo global. Una referencia archivada o eliminada sólo se conserva si el mismo ID de aparición ya estaba ligado a ese mismo ejercicio en el borrador actual o en la versión sellada propia de la misma rutina indicada como base. Un ID de aparición nuevo no hereda esa excepción. La versión base puede ser anterior a la actual; sirve como procedencia, sin publicar ni actualizar la raíz.

Una revisión obsoleta conserva el comando canónico completo como conflicto, incluido texto y fecha original. Se limita el grupo completo antes de guardar la propuesta; si ésta no cabe, el resultado terminal es `LIMIT_EXCEEDED` y el cliente debe conservar su captura local. Las mismas defensas de tamaño canónico/JSONB de 1B se aplican a los guardados. Los fallos después de guardar el borrador o después del journal revierten cambios, propuesta, recibo y secuencia.

Las pruebas 1C cubren cadena crear→guardar, dependencia pendiente/bloqueada/ajena/antigua, CAS concurrente y reintento, propuesta íntegra, referencias históricas por aparición, base anterior sellada, aislamiento, autoridad, descarte simulado como prerrequisito, raíz retirada y límites. Las versiones que preparan esas pruebas son fixtures explícitas de historia existente; no acreditan por sí solas un productor de publicación ni su hash. ## Publicación: bloque 1D

`PublishRoutine` comprueba la raíz y `payload.draft_revision` exactos antes de resolver cualquier snapshot de ejercicio. La base por recibo corresponde a `routine`: un recibo que sólo afectó `routine_draft` no sirve como base raíz. Si cambió la raíz o el borrador se conserva una propuesta de publicación, ligada a las revisiones respectivas. El comando no contiene el texto del borrador; la revisión histórica del borrador sigue disponible en `record_revisions`. No se añade un campo no contractual al conflicto ni se presenta esta conservación como una UI completa de resolución.

El mapa debe cubrir cada día y aparición exactamente una vez, con UUIDs nuevos y destinos sin duplicados. El orden de la versión viene del borrador, no del orden de ese mapa. Se exige título, etiquetas e indicaciones legibles, al menos un día, ejercicios en todos los días y series prescritas; texto, Unicode y espacios válidos se conservan exactamente. No se inventa contenido para completar un borrador.

Los ejercicios activos congelan nombre y modo de carga actuales al resolver el material en la transacción. Los retirados sólo se admiten cuando la misma aparición y referencia tienen un snapshot verificable en `base_version_id`, sellada, propia y de la misma rutina. En ese caso se usa el nombre/modo históricos, mientras prescripción, notas y orden vienen del borrador. Una referencia retirada sólo ligada a un borrador sin snapshot sellado no puede publicarse; su rechazo conserva el borrador. No existe una revisión de ejercicio suministrada por el cliente: el CAS contractual es de raíz y borrador.

La publicación crea versión/días/apariciones nuevos, sella la versión y actualiza la raíz a `ready`, con título/puntero y revisión creciente. Consume el borrador como tombstone: revisión siguiente, `base_version_id` de la nueva versión, contenido nulo y fecha de servidor. Una siguiente edición parte de esa revisión, no de cero. Versión inmutable de revisión `1`, raíz y tombstone se emiten juntos en un grupo y recibo. El contador de versión está limitado a int32.

El hash usa el helper común sobre el DTO completo salvo `content_hash`; no tiene prefijo ni normaliza texto. Las serializaciones internas se canonicalizan antes de aplicar límites de transporte para que escapes HTML opcionales no rechacen contenido válido. `CheckChanges` mide versión/grupo canónico y defensa JSONB antes de efectos. Un savepoint SQL estrecho permite deshacer todas las inserciones de una publicación ante cualquier colisión global de versión/día/aparición y guardar un rechazo genérico en la misma transacción exterior, sin consultar ni revelar propietarios ajenos. No hace commits internos ni elimina historias conservadas.

Las pruebas 1D producen versiones reales, verifican su hash reconstruido desde PostgreSQL, grupo completo, replay concurrente, ambos CAS antes de snapshots, colisiones propias/ajenas y concurrentes, rollback después del agregado y journal, permisos/sellado, aislamiento, retiro de autoridad, rename/archive tras v1 y tamaños. Las unitarias incluyen un DTO cuyo JSON escapado supera 2 MiB pero su canónico cabe, sin usarlo para eludir límites HTTP. El bloque sigue pendiente de la corrida PostgreSQL central, integración HTTP y validación del usuario; no acredita entrenamiento móvil ni selección/descarga completa.

## Inicio de entrenamiento: bloque 1E

`StartWorkout` admite exclusivamente `workout.start`, base `0`, y crea un entrenamiento en curso de revisión `1`, sin resultados ni series realizadas. La autoridad procede de una sesión vigente en el momento de sincronizar; el dispositivo de origen debe pertenecer a la cuenta y puede estar retirado cuando sólo aporta procedencia histórica. El actor se valida antes de recuperar cualquier recibo.

El servidor lee una versión propia sellada, comprueba su hash completo y exige que el día y el mapa de apariciones coincidan exactamente. Copia de esa versión el título, etiqueta, referencia, nombre, modo, orden, prescripción y notas, usando los nuevos UUIDs del cliente. No consulta valores actuales de ejercicios ni exige que la rutina siga en la biblioteca: un archivo, baja o publicación posterior no impide registrar el entrenamiento de una versión descargada, ni restaura la rutina. El orden del mapa se conserva en el hash del comando; el orden del snapshot procede del día publicado.

La raíz, todas sus apariciones, el sello, la proyección `workout`, una secuencia y el recibo se comprometen juntos. Un savepoint interno deshace sólo las inserciones ante colisiones globales de UUIDs, permitiendo un rechazo durable genérico sin descubrir propietarios. No se sobrescriben entrenamientos anteriores ni se fusionan dos identidades independientes por tener la misma fecha o contenido. La defensa del repositorio vuelve a comparar la copia completa contra la versión sellada antes de escribir.

`started_at` es el instante aportado por el dispositivo y no se ordena, corrige ni limita por la fecha del servidor o publicación. `captured_at` se pasa con su texto original al recibo común; la migración y persistencia de ese metadato son responsabilidad del bloque central 064. Creación/actualización usan fecha de servidor UTC con milisegundos. El puerto de zona horaria exige pertenencia al catálogo IANA embebido y carga válida, sin fallback: no admite `Local`, vacío, `localtime`, `posixrules` ni rutas del host. `iana_names.txt` se extrajo del `lib/time/zoneinfo.zip` del toolchain Go y debe actualizarse junto con la base de zonas al actualizarlo. El dominio no lee la zona ambiental ni el reloj.

Las unitarias verifican forma cerrada, mapa, copia independiente, tiempos y catálogo. Siete pruebas PostgreSQL cubren productores reales de publicación e inicio, replay concurrente, dos identidades distintas, material inválido, versión histórica, A/B, origen retirado y actor vigente, colisiones, rollback después del agregado y journal, sello/completitud, fechas y máximo contractual. Con 50 apariciones y los límites actuales de texto, un workout válido máximo todavía cabe por debajo de 1 MiB; se prueba realmente ese máximo y se inyecta aparte un error de preflight para verificar el rechazo terminal, sin presentarlo como una frontera real de 1 MiB. No se ejecutaron estas pruebas contra el fixture compartido: esperan la corrida PostgreSQL central.

## Series y envío por lotes: bloque 1F

`CreateWorkoutSet` crea una serie de revisión1 con identidad propia, sin deduplicar por peso, posición o repeticiones. La base de la nueva serie es0. `observed_workout` resuelve la revisión explícita o el efecto exacto de un recibo propio; un padre ausente deja pendiente sin recibo terminal, uno fallido bloquea esa rama. Una revisión observada anterior válida no descarta una serie independiente. El actor actual debe seguir vigente; el origen histórico pertenece a la misma cuenta.

La aparición se toma del snapshot inmutable del entrenamiento. El modo de carga debe coincidir; `none` conserva valores nulos y cero externo conserva peso/unidad explícitos. La proyección usa decimal exacto de escala3, mientras el cuerpo y hash conservan el texto original. Perfil y ejercicio actuales no reinterpretan el resultado. Cada ID cuenta para el máximo1000 del entrenamiento, incluyendo series eliminadas.

Serie y avance de raíz se escriben en la misma transacción y grupo. Si el entrenamiento terminó, se conservan finished_at/finalized_revision y se añade revisión pendiente y conflicto completo junto al resultado `accepted_with_review`. Si fue eliminado, se conserva sólo la propuesta como conflicto, sin resucitarlo ni crear la serie. El target del conflicto es workout/payload.workout_id. Los prerequisitos de finalización/eliminación de estas pruebas son fixtures SQL explícitas; no acreditan productores ni carreras E2E de esas acciones aún ausentes.

`PushWorkouts` acepta una unión cerrada de inicio y creación de serie. Valida toda la gramática, tamaño canónico y duplicados, separa una copia de los comandos y comprueba actor/orígenes antes del primer efecto. Después ejecuta en orden, una transacción por comando, con plazo global30s; no promete atomicidad del lote. Un mismatch no revela ni reemplaza el recibo anterior. Revocación durante el lote conserva resultados previos y requiere autenticación para los restantes; errores temporales conservan reintento individual. El ID HTTP identifica la petición, los IDs de operación gobiernan deduplicación.
