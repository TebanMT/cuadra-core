# Solicitud de eliminación

Este bloque registra la aceptación de la solicitud. No ejecuta purga, libera un teléfono, destruye llaves, borra archivos locales ni habilita usuarios reales. La política se inyecta con versión y demora de purga explícitas; no hay valores predeterminados. Ausente devuelve `POLICY_NOT_CONFIGURED` antes de tocar la base o consumir una prueba. Los valores de los fixtures son sintéticos y no representan una decisión de retención aprobada.

`RequestAccountDeletion` recibe el actor verificado por middleware y exige contexto de cuenta puro. En una transacción auth con el mutex compartido por sync: comprueba sesión, liga operación/hash, consume el proof de `delete_account`, pasa la cuenta a `deletion_pending`, incrementa sólo `security_version`, registra política/fechas y revoca todas las sesiones. Cancela desafíos vinculados no consumidos y sus autorizaciones pendientes/aprobadas. El recibo y el evento mínimo forman parte del mismo commit. Cualquier error revierte también el proof. El repositorio exige encontrar ese consumo exacto antes de modificar la cuenta.

Se conservan teléfono, dispositivos, verificadores, envelopes del vault y contenido. La cuenta inactiva impide usarlos para reautorizarse, renovar, desbloquear o subir pendientes. No se modifica la revisión del perfil ni se escribe un journal desde el pool auth. Los intentos todavía sin cuenta quedan fuera del ámbito RLS; su resolución posterior no puede autorizar una cuenta inactiva. No se promete cancelar todos los mensajes ya enviados.

Antes del POST, el cliente debe guardar operación, cuerpo y `result_secret` aleatorio de 32 bytes. Se conserva sólo SHA-256 de una representación con separación de dominio, UUID de operación y esos bytes. Así reutilizar accidentalmente un secreto en otra operación produce otro hash. La función SQL existente resuelve por hash; el lector vuelve a exigir propietario, operación, propósito y hash exactos, además de una transición de eliminación confirmada. Un hash duplicado por corrupción puede impedir la lectura, pero no devolver un recibo ajeno.

`GetDeletionResult` acepta exclusivamente un contexto originalmente anónimo. El secreto limitado puede obtener sólo el Ack de la aceptación original —operación, `deletion_pending` y fecha—, aun después de retirar las sesiones. No abre ciphertext ni devuelve cuenta, perfil, sesiones, kit o llave. No usa la ventana de diez minutos de las respuestas con credenciales. El recibo permanece hasta una política de mantenimiento futura; su existencia no demuestra que se ejecutó la purga. El POST normal nunca omite `SessionActive` para recuperar una respuesta perdida: se usa esta lectura limitada.

Las pruebas de PostgreSQL requieren DSN locales del harness y se omiten sin ellos. Cubren política ausente, proof vencido o incorrecto, rollback posterior al efecto/evento, concurrencia, cuenta A/B, respuesta perdida, secreto reutilizado/incorrecto, ámbitos, rol data, refresh, vault, reenvío y límites de pull/escritura tras aceptación. No acreditan todavía HTTP/móvil, purga por categorías o restauración. Un evento almacenado en el mismo respaldo antiguo no basta para reaplicar bajas posteriores: hacen falta el registro operativo independiente y el ensayo de restore de MC-P05. MC-P04 conserva pendientes los plazos de retención, respaldos, auditoría y reutilización del número. US011 sigue pendiente de implementación integrada y validación del usuario.
