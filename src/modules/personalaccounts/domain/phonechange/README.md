# Cambio de teléfono

`StartPhoneChange` y `CompletePhoneChange` admiten sólo una cuenta autenticada sin ámbito de intento ni gym. El desafío pertenece a la cuenta y conserva el candidato exacto del dispositivo registrado. El recibo inicial liga cuenta, sesión, dispositivo, intento y operación con un digest de valores de longitud fija. Renovar el JWT o refresh conserva ese vínculo; otra sesión del mismo dispositivo no lo hereda.

Cada petición usa una prueba de dispositivo propia, de propósito `phone_change`, ligada al hash protegido que incluye ruta, cuerpo e ID de operación. La prueba inicial se consume con el intento de envío. La prueba de completar se valida antes de reservar la llamada Check y se consume sólo con el cambio de identidad. Si vence entre ambas fases, un proof nuevo para la misma petición puede terminar un Check ya acreditado sin consultar de nuevo al proveedor.

| Fase | Commit | Fallo |
| --- | --- | --- |
| Inicio | Presupuesto de envío, desafío, operación de proveedor, prueba inicial, vínculo del iniciador y evento | Todo revierte; mismo teléfono no reserva ni envía |
| Check | Presupuesto de comprobación, operación de proveedor y recibo reservado | Fallos previos revierten; un Check negativo o incierto conserva la reserva |
| Hecho del proveedor | Resultado directo de la operación exacta y su revisión | Un resultado tardío no revive un intento cancelado; 404 no prueba aprobación |
| Cambio | Consumo de proof e intento, teléfono, versión de seguridad, rotación de sesión, cierre de otras sesiones, cancelación de intentos vinculados, recibo cifrado y evento | Todo el efecto revierte; el hecho OTP y su reserva anterior permanecen para el reintento original |

`PreparedCommand` sólo existe para el pool auth. Acepta cuenta pura y usa la misma transacción read committed para preparación y efecto. La preparación de la aplicación adquiere presupuesto → teléfonos en orden del HMAC → mutex de cuenta. Las lecturas previas no toman el mutex. Se vuelve a leer el teléfono después de adquirirlo: una observación obsoleta reinicia la transacción completa, nunca añade un tercer bloqueo en orden invertido. La función es una capacidad de código interno confiable, no una restricción SQL de sólo lectura.

La sesión iniciadora conserva SID, DID y familia; cambia a generación +1, refresh nuevo y ticket nuevo, con 90 días de inactividad. El historial guarda los hashes de refresh/ticket anteriores sin ciphertext. Por ello `/auth/refresh` no puede recuperar una respuesta del cambio de teléfono, pero el ticket anterior sigue pudiendo cerrar exactamente la misma sesión. Las otras sesiones se revocan; no se retiran dispositivos ni se rota el kit. Cambian `security_version`, `phone_changed_at` y `updated_at`, nunca la revisión del perfil ni el journal.

El recibo de completar mantiene la ventana original de diez minutos desde la reserva de Check. Repetir el mismo POST devuelve la respuesta original sólo al SID/DID original todavía activo, antes de exigir que el proof siga vigente. Después de otro refresh puede devolver credenciales históricas de una generación inferior: no las instala ni las vuelve a habilitar en servidor. El cliente debe conservar su generación más reciente. Al vencer se conserva el recibo y se devuelve `RESULT_EXPIRED`; nunca se crea otra sesión. No hay excepción para una sesión revocada.

`GetPhoneChangeAttempt` y `ResendPhoneChange` usan las rutas contractuales de consulta/reenvío mediante un despachador que separa estos intentos de acceso y recuperación. Exigen un contexto inicialmente anónimo y la continuación exacta del intento. El resolvedor consulta únicamente ese ámbito auth, lee el SID del recibo inicial y verifica su digest antes de derivar la cuenta; después comprueba bajo mutex que la sesión iniciadora sigue activa. No hay un lookup global ni se elimina un ámbito heredado para hacerlo válido. El recibo inicial guarda el SID en `result_reference`; su propietario ya conserva el ID del intento.

La consulta devuelve sólo el intento, incluso verificado o consumido: nunca devuelve sesiones, kit ni autorización de acceso. Puede consultar al proveedor después de la demora configurada si conoce su referencia, pero `Fetch approved` y 404 nunca acreditan un Check directo. Sin referencia conserva la incertidumbre. El reenvío exige una acción explícita nueva, respeta el TTL original, cooldown y los tres presupuestos compartidos, y sólo puede cambiar entre WhatsApp y SMS para el mismo destinatario y candidato. El proof inicial autoriza esa continuación limitada; completar todavía exige el JWT del iniciador y su propio proof. Repetir una operación de reenvío devuelve su estado sin enviar ni gastar otra vez. La sesión se vuelve a validar antes de aplicar cualquier resultado tardío del proveedor.

No hay reenvío ni Check automático. La cancelación alcanza desafíos con `account_id` propio visibles por RLS y sus autorizaciones no consumidas. Los desafíos sin cuenta y los resultados consumidos siguen su política original. Las pruebas de esta ampliación y su montaje HTTP requieren la siguiente ejecución del harness central; no acreditan integración móvil ni un envío real de Twilio.

`GetPersonalAuthResult` implementa la lectura autenticada de resultados de `phone_change_complete` y `recovery_key_rotate`. Usa una lista cerrada de propósitos; no acepta secretos de intento o eliminación y nunca inicia efectos. El repositorio devuelve el recibo propio y, para teléfono, sólo un booleano que acredita el desafío consumido correspondiente, sin seleccionar su secreto de continuación. Después se comprueba actor exacto, ventana y contenido del envelope. Un kit sustituido no se devuelve como vigente. Otras clases de resultado y la capacidad limitada de eliminación siguen pendientes; HTTP y móvil se coordinan por separado.

Las pruebas PostgreSQL usan sólo los DSN locales explícitos del harness; sin ellos se omiten. El proveedor HTTP de estos casos es sintético. Las claves, teléfonos y credenciales de fixtures no autorizan tráfico real.
