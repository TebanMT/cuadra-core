# Intentos de autenticación — componente parcial

`domain/attempt.AuthAttempt` representa la fila `mancuerna.auth_challenges` de las migraciones 059/060. No crea cuentas, autoriza equipos, emite sesiones ni verifica un kit de recuperación. El candidato, nonce, destino, propósito, ID propuesto y hashes iniciales forman un binding inmutable. El único vínculo de cuenta posterior permitido es `nil → cuenta` desde `verified`, una vez que el coordinador central acreditó y bloqueó esa identidad. Recuperación vincula una cuenta existente; `proposed_account_id` nunca es autorización para crearla. Cambio de teléfono requiere la cuenta vinculada desde el inicio.

La construcción requiere la vigencia conocida del proveedor, sin valor implícito. El límite local es diez minutos y se reduce ante una fecha real anterior del proveedor; nunca se extiende por reenvío. Las fechas creadas por el dominio son UTC con precisión de milisegundos. Los estados de autorización de otro equipo se derivan fuera de esta entidad y no se inventan estados adicionales en la tabla.

`ReserveSend` y `ReserveCheck` guardan una intención con UUID de operación, hash de petición, tipo, fecha y revisión antes de invocar al proveedor. Ambos dejan `uncertain`; check también incrementa `attempts` y exige un máximo positivo configurado. El caller debe confirmar esa transacción corta antes de la llamada externa. Un resultado sólo se aplica con el `OperationToken` exacto de la reserva y con la referencia/canal esperados. La aprobación de un envío no acredita posesión; sólo un check aprobado puede producir `verified`.

`ApplyOutcome` recibe hechos conocidos del puerto de verificación. Timeout, recurso ausente o 404 no se pasan como aprobación. Ante una caducidad real ya cumplida, el método guarda `expired`, incluso si el proveedor informó `approved`; un retorno sin error exige inspeccionar el estado resultante. La referencia reutilizada puede haber vencido antes de crear el intento local: esa fecha se conserva en el intento terminal, sin autorización. Si ya venció el plazo local antes de aplicar el resultado, se devuelve el error de caducidad y `Expire` permite persistir el estado terminal.

Para una nueva petición **explícita** del usuario, `ReleaseUncertain` admite liberar la incertidumbre tras un intervalo positivo configurado. El coordinador debe consultar primero al proveedor si hay referencia y reservar los límites correspondientes. La liberación no envía, no borra el fingerprint, no extiende el plazo y aumenta la revisión; una respuesta de la operación anterior ya no puede sobrescribirla. La entidad conserva sólo la última operación: `auth_receipts`, a cargo del coordinador, debe conservar el historial de IDs/hashes para impedir repetir efectos de operaciones antiguas. No hay reenvío automático.

El repositorio `AuthAttemptPostgresRepository` recibe siempre una transacción del pool personal de autenticación. `Get` y `GetForUpdate` exigen ID y hash de continuación explícitos, además de RLS. `Save` bloquea la fila, comprueba CAS, identidad inmutable, comprobantes conservados y transiciones de cuenta; escribe una lista cerrada de columnas mutables. Acepta varias transiciones dentro de una transacción (`revision > expectedRevision`), sin commits propios. Antes de vincular cuenta, la aprobación debe estar guardada como `verified`. El camino directo es persistir ese resultado OTP en una transacción corta y después resolver identidad, `BindAccount`, `Consume`, sesión y recibo en otra transacción atómica. La posesión OTP persistida por sí sola no autoriza acceso. El orden global teléfono → cuenta → fila del intento pertenece al coordinador: no ejecutar primero `Save`/`GetForUpdate` y después adquirir mutex de teléfono/cuenta, salvo que el caller ya haya tomado el orden global. El repositorio no sustituye esa coordinación.

No se guardan OTP, secreto de continuación, secreto de recuperación ni cuerpos del proveedor. Los errores PostgreSQL se reducen a errores seguros y estas consultas desactivan el logger SQL para evitar valores privados en errores de GORM. El wiring futuro debe mantener el pool auth completo con diagnósticos que tampoco registren las credenciales de contexto.

Pruebas unitarias/race y compatibilidad del dominio con sidecar cubren binding, límites, estados terminales, check sin referencia, máximo de comprobaciones, cambio de canal, reloj, firma de operación, respuesta tardía, incertidumbre y caducidad. `python3 tests/mancuerna/attempt_run.py` inicia PostgreSQL desechable por socket Unix, aplica 059/060 y usa un login restringido de auth. Exige cinco pruebas reales: aislamiento/binding, incertidumbre durable/rollback/CAS, reservas concurrentes, vínculo/consumo y caducidad/redacción. No lee `.env`, `DATABASE_URL`, conexiones existentes ni Twilio; el resultado y hashes quedan en `/tmp/mancuerna-attempt-*/result.json`.

Este componente está implementado y pendiente de integración/validación. No completa US-001/002/009 ni un recorrido de cuenta: faltan coordinación OTP/proveedor real de pruebas, presupuestos, recibos, pruebas de dispositivo/kit, autorización de equipos, sesiones, handlers y móvil. Ninguna historia pasa a DONE por estas pruebas.
